## 2. Описание проекта

### Питч
**«Капля»** — PWA, которое показывает центры крови на интерактивной карте, отражает потребности центров в реальном времени и отправляет донору уведомление, когда в его городе нужна именно его группа крови.

### Проблема
Центрам крови часто не хватает редких групп в конкретном городе. Информация о потребностях разрознена (чаты, сайты, соцсети); доноры узнают о срочных запросах слишком поздно.

### Решение
Собрать потребности центров в одном месте и доставлять их адресно: карта + живая лента + push по профилю донора (группа крови + радиус).

### Ключевые функции MVP
1. **Карта центров** — геолокация, ближайшие центры, карточка (адрес, режим, нужные группы);
2. **Живая лента потребностей** — группа, объём, срочность, прогресс, автообновление;
3. **Push-уведомления** — по профилю донора и радиусу;
4. **Профиль и запись на донацию** — группа, радиус, выбор центра и времени, история.

### Критерии успеха
- число подписчиков на уведомления;
- конверсия из уведомления в запись/донацию;
- среднее время от публикации заявки до отклика;
- процент закрытия срочных заявок.

### Ограничения и регуляторные основы
- Явное согласие на геолокацию и push;
- Контроль интервала между донациями (не чаще, чем допускает Минздрав);
- Достоверность данных заявок (модерация/статусы);
- Приватность персональных данных.

## 3. Целевая аудитория

### Сегменты
| Сегмент | Боль | Потребность |
|---|---|---|
| Активные доноры с редкой группой | Не знают, когда нужна их кровь | Получать адресные уведомления и быстро записываться |
| Начинающие доноры | Не знают, куда идти, как записаться | Понятная карта, простая запись, онбординг |
| Центры/станции переливания (B2B) | Заявки закрываются медленно | Публиковать потребности, видеть отклики |

### Роли в системе
| Роль | Возможности |
|---|---|
| **Гость** | Просмотр карты, ленты, карточек центров |
| **Донор** (авторизованный) | Профиль, подписка на push, запись, история, отмена/перенос |
| **Координатор центра** | Публикация/редактирование заявок, просмотр откликов, статистика (Should/Nice) |

## 6. Обработка ошибок

### Принципы UX
- **Видимость** — ошибка сообщается явно и вовремя;
- **Понятность** — человеческим языком, без кодов;
- **Обратимость** — всегда есть «Повторить», «Изменить», «Отменить»;
- **Ненавязчивость** — Minimalist-тон; красный только для блокирующих ошибок и статусов «Срочно/Критично».

### Обязательные сценарии по типам ошибок

| Тип | Обязательное поведение | Где |
|---|---|---|
| **Валидация** | Подсветка поля + текст под ним; блокировка сохранения; автофокус на первом некорректном поле | все формы |
| **Отсутствие данных** | Пустое состояние с иконкой, пояснением и действием («Изменить радиус», «Сбросить фильтры», «Включить push») | карта, лента, история |
| **Сеть** | Скелетон при загрузке; баннер «Нет соединения» + «Повторить»; автосохранение черновиков; плашка «Данные устарели»; офлайн-кэш | все экраны |
| **Неавторизованный доступ** | Гостевой просмотр; вход перед действием с возвратом к намерению; «Нет доступа» для координатора | запись, push, B2B |

### Ключевые негативные сценарии (из `error_handling.md`)

| Функция | Сценарий | UX-решение |
|---|---|---|
| Профиль | Нет группы крови | Подсветка + «Укажите группу крови» |
| Профиль | Радиус 0 или >500 км | «Радиус от 1 до 500 км» |
| Карта | Нет центров в радиусе | Пустое состояние + «Изменить радиус» |
| Карта | Геолокация запрещена | Баннер + ручной ввод адреса |
| Лента | Фильтр пуст | «Сбросить фильтры» |
| Лента | Сбой автообновления | «Обновить сейчас» |
| Push | Разрешение отклонено | Инструкция «Как включить» |
| Запись | Слот занят | «Выберите другое время» |
| Запись | Интервал < 60 дней | «Интервал не соблюдён» |
| B2B | Нет роли координатора | «Только для координаторов» |

## 7. Модель данных (MVP)

| Сущность | Ключевые поля | Связи |
|---|---|---|
| **Донор** | id, телефон, группа крови, резус, радиус, согласия (гео/push), дата последней донации | 1 → N Записи |
| **Центр** | id, название, адрес, координаты, график, телефон, статус «проверенный» | 1 → N Заявки |
| **Заявка (потребность)** | id, центр_id, группа, объём, срочность, прогресс, статус (активна/закрыта), created_at | N → 1 Центр |
| **Запись** | id, донор_id, центр_id, дата, время, статус (ожидает/подтверждена/отменена/не состоялась) | N → 1 Донор, N → 1 Центр |
| **Отклик** | id, заявка_id, донор_id, created_at | N → 1 Заявка |
| **Уведомление** | id, донор_id, тип, текст, статус доставки | N → 1 Донор |
| **Настройки** | донор_id, типы уведомлений, частота | 1 → 1 Донор |

Примечание: для MVP данные могут храниться в mock-слое на клиенте (localStorage/IndexedDB) с теми же полями.

## 8. API и данные (Mock)

ТЗ стек-агностично. Для MVP допускается mock-слой данных вместо реального бэкенда. Обязательный набор операций (контракт):

| Операция | Назначение | Связанные FR |
|---|---|---|
| `GET /centers` | Список центров с координатами и графиком | FR-2 |
| `GET /requests` | Список заявок (лента) с фильтрами и пагинацией | FR-3 |
| `POST /requests` | Публикация заявки координатором | FR-7 |
| `PATCH /requests/{id}` | Редактирование/закрытие заявки | FR-7 |
| `POST /appointments` | Создание записи на донацию | FR-5 |
| `PATCH /appointments/{id}` | Отмена/перенос записи | FR-5 |
| `POST /subscriptions` | Подписка на push | FR-4 |
| `GET /donors/{id}/history` | История донаций | FR-6 |

Формат ответов — JSON. Ошибки API возвращаются с человекочитаемым сообщением и кодом; клиент преобразует их в UX-сообщения по разделу 6.

## 9. Definition of Done (критерии готовности)

1. Реализованы **все FR с приоритетом Must** (FR-1…FR-8) и подтверждены критериями приёмки Given/When/Then из `user_stories.md` (Приложение А).
2. Обработка ошибок соответствует матрице `error_handling.md` для всех функций MVP.
3. PWA устанавливается, работает офлайн (Service Worker, кэш), данные ранее просмотренных экранов доступны без сети.
4. Интерфейс соответствует концепции **Minimalist**: mobile-first, адаптивность от 320px, стиль и палитра.
5. Проверено в Chrome, Safari, Firefox, Edge (последние 2 версии) и на Android/iOS.
6. Доступность: навигация с клавиатуры, контраст ≥ 4.5:1, читаемые сообщения на русском.
7. Код задокументирован; README описывает запуск и структуру проекта.

## 10. Ограничения и допущения

- **MVP без реального бэкенда:** допускается mock-слой данных на клиенте; контракт API (раздел 8) остаётся целевым для будущей интеграции.
- **Регистрация:** для MVP — вход по номеру телефона с одноразовым кодом (или его имитация в mock); полная верификация — вне MVP.
- **Данные центров:** предоставляются вручную/моком; автоматическая интеграция с региональными базами — вне MVP (Nice).
- **Геолокация:** используется с явного согласия; при отказе — ручной ввод адреса.
- **Интервал донаций:** фиксированное правило ≥ 60 дней (рекомендация Минздрава), конфигурируемое.
- **Push:** в MVP — Web Push; на iOS — через PWA-поддержку браузера.
- **Масштаб:** MVP покрывает одного пользователя-донора и координатора центра; B2B-дашборд для компаний — Nice (FR-9.6).
