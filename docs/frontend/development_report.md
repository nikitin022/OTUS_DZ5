# Отчёт о процессе разработки — PWA «Капля»

Проект разработан по итеративному процессу: каждый шаг начинался с плана
(анализ кодовой базы → план с trade-offs), выполнялся AI-агентом и завершался
коммитом и пушем в GitHub. Полные технические детали — в документах из
[README](../README.md#документация).

## 1. Ход работы по шагам

| Шаг | Что сделано | Ключевой результат |
|---|---|---|
| 1. ТЗ | Зафиксированы стек (React+TS+Vite, Tailwind, Leaflet, TanStack Query) и требования (5 блоков Must) | `docs/stack_decision.md`, `docs/functional_requirements.md` |
| 2. Инициализация | Каркас Vite+PWA, конфиги, `rules.md`, UI-токены Minimalist | Рабочий дев-сервер, сборка, линт |

| 4. UI-компоненты | Mock-слой данных (контракт ТЗ, раздел 8), «живая» лента, экраны с состояниями loading/error/empty | 51 тест, работающие экраны на данных |
| 5. Тестирование и отладка | Интеграционные тесты, реализация флоу записи, 5 багов найдено и исправлено | 61 тест; BUG-1…BUG-5 |
| 6. Адаптивность | Аудит 320–1440 px сканером переполнений, адаптивная навигация, safe-area, анти-зум iOS | RESP-1…RESP-5 исправлены |

| 8. Оформление | README, отчёт, деплой на GitHub Pages | Демо-URL, финальная проверка |

## 2. Техники работы с AI

1. **Планирование до кода.** Каждый шаг начинался в режиме анализа: AI собирал
   факты (grep-аудит, замеры в браузере), формулировал план с альтернативами и
   trade-offs, и только затем выполнял. Это исключало «слепую» генерацию.
2. **Правила проекта (`rules.md`).** Язык интерфейса, архитектурные ограничения
   (доступ к данным только через `ApiClient`), стиль коммитов — заданы один раз
   и применялись во всех генерациях.
3. **Генерация по образцу.** Новые компоненты создавались в стиле существующих
   (та же система токенов, те же пропсы, тот же язык сообщений), а не «с нуля».
4. **Отладка по свидетельствам.** Скриншоты разбирались мультимодально
   (ожидание vs реальность → воспроизведение → фикс), ошибки консоли — по
   схеме «суть → причина → гипотезы → минимальный фикс + регрессионный тест»
   (шаблоны: `docs/ai_debugging_prompts.md`).
5. **Браузерная верификация через Chrome DevTools (MCP).** Обход всех экранов,
   мониторинг консоли, авто-сканер переполнений на 5 ширинах, замер computed
   styles — AI проверял собственную работу по реальному DOM, а не только тестами.
6. **Метрики вместо ощущений.** Цели формулировались измеримо: размер чанков,
   число тестов, количество дублей — и проверялись после выполнения.
7. **Тесты как страховка рефакторинга.** Существующие 79 тестов определили
   критерий «поведение не изменилось»; регрессионные баги становились тестами.
8. **Право отказаться.** Там, где обобщение ухудшало код (лента со своей
   логикой частичных сбоев), рефакторинг сознательно не проводился.

## 5. Итоговые метрики

- **Тесты:** 85/85 в 17 файлах (unit + интеграционные; позитивные, ошибочные
  и пограничные сценарии);
- **Качество:** ESLint 0 ошибок / 0 предупреждений; `tsc` strict без ошибок;
- **Производительность:** главный бандл 292 КБ (gzip 93 КБ) вместо 451 КБ
  (gzip 139 КБ) — Leaflet вынесен в ленивый чанк; NFR-1 (TTI ≤ 5 с на 3G)
  выполняется с запасом;
- **Требования:** реализованы все Must-функции FR-1…FR-8, матрица ошибок ТЗ,
  адаптивность от 320px, PWA-установка и офлайн-кэш.

## 6. Выводы и рекомендации

1. **План → факт → верификация** — самая продуктивная петля работы с AI:
   агент сначала собирает факты об кодовой базе и браузере, потом меняет код,
   потом сам проверяет результат теми же инструментами.
2. **Тесты как контракт** позволяют агента рефакторить смело: критерий
   «поведение не изменилось» проверяется автоматически, а не на глаз.
3. **Правила проекта окупаются на втором шаге**: `rules.md` избавил от
   повторных объяснений стека, языка интерфейса и стиля коммитов.
4. **Браузер — источник истины**: часть багов (пропавшие шапки, «Центр № c-1»)
   не ловится ни юнит-тестами, ни типами — только реальным DOM.
5. **Рекомендации дальше**: подключить реальный бэкенд (контракт `ApiClient`
   уже готов), покрыть E2E-сценарии Playwright, добавить push-уведомления
   через серверную часть (FR-4.1), контур координатора (FR-7/FR-8) и
   офлайн-очередь записей.
