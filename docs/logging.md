# Логирование и анализ логов «Капля»

Бэкенд работает на Supabase — логи собираются платформой автоматически, собственный лог-сервер не требуется (следствие решения `docs/infrastructure_decision.md`). Доступ: дашборд проекта → **Logs** (или Logs API/Explorer).

## 1. Источники логов

| Источник | Что содержит | Когда смотреть |
|---|---|---|
| `edge_logs` (API Gateway) | Каждые HTTP-запрос: метод, статус, путь, user-agent | 4xx/5xx, аномальная частота, безопасность |
| `postgrest_logs` | Жизненный цикл PostgREST: перезагрузки кэша схемы, пул соединений | После миграций (смена кэша), проблемы соединений |
| `postgres_logs` | Ошибки и долгие SQL-запросы БД | Медленные запросы, ошибки SQL, блокировки |
| `auth_logs` | Вход/OTP: код ошибки, IP, длительность | Проблемы входа, подбор кодов, спам OTP |
| `pgbouncer_logs` | Пул соединений БД | Таймауты соединений под нагрузкой |
| `realtime_logs` | Realtime-каналы | Проблемы подписок в реальном времени |

Фактический состав источников в проекте (за окно наблюдения): `pgbouncer_logs` 2172, `postgrest_logs` 91, `postgres_logs` 40, `edge_logs` 15, `auth_logs` 3, `realtime_logs` 2 события.

## 2. Формат ошибок, которые видит клиент

Все ошибки API доходят до UI как `ApiError` с человекочитаемым сообщением (единый маппинг `src/api/errorMessages.ts`, матрица ошибок ТЗ разд. 6):

| Источник ошибки | Код | Сообщение пользователю |
|---|---|---|
| Сетевой сбой (offline, таймаут) | `NETWORK_ERROR` | «Нет соединения с сервером…» |
| JWT истёк | `PGRST301` | «Сессия истекла. Войдите заново…» |
| Нарушение RLS | `42501` | «Недостаточно прав для этого действия.» |
| Уникальность (дубль отклика и т.п.) | `23505` | «Такая запись уже существует.» |
| Бизнес-правило RPC | `P0001` | Текст из БД («Слот занят…», «Интервал не соблюдён…») |
| Не найдено | `PGRST116` | «Запись не найдена или данные изменились.» |
| Серверная ошибка | `58000`/`XX000` | «Внутренняя ошибка сервера. Попробуйте позже.» |
| RPC/таблица недоступна без прав | `42501` (permission denied) | Текст PostgreSQL или «Недостаточно прав…» |

## 3. Пример анализа логов (реальный разбор, 2026-09-22)

Запрос к Logs API по окну тестирования endpoints (curl-тесты Шагов 4–5 и живая проверка):

```sql
select event_message, count(*)
from logs
where source = 'edge_logs'
group by 1 order by 2 desc;
```

Результат (все HTTP-обращения к API за окно):

| Запрос | Статус | Интерпретация |
|---|---|---|
| GET /rest/v1/centers | 200 | Чтение справочника — норма |
| GET /rest/v1/blood_requests?status=eq.active… | 200 | Фильтрация ленты — норма |
| GET /rest/v1/appointments | 200 | Приватные данные гостю скрыты (`[]`) — RLS работает |
| PATCH /rest/v1/appointments?id=eq.0000… | 204 | RLS: гостю недоступны чужие строки — 0 изменённых, норма |
| POST /rest/v1/blood_requests | 401 | Ожидаемое: запись без авторизации заблокирована RLS |
| POST /rest/v1/rpc/create_appointment | 401 | Ожидаемое: RPC закрыт от гостей (`permission denied`) |
| POST /rest/v1/rpc/register_donor_profile | 401 | Ожидаемое: RPC закрыт от гостей |
| PATCH /rest/v1/appointments?id=eq.0000… | 400 | Первый прогон curl: пустое тело (ошибка тестового скрипта), затем исправлено |
| POST /rest/v1/blood_requests, /rpc/* | 400 | Первый прогон curl: JSON не дошёл (BOM/кавычки PowerShell), исправлено |
| POST /auth/v1/otp | 400 | `phone_provider_disabled` — SMS-провайдер не подключён (операционная настройка) |
| POST /auth/v1/verify | 403 | `otp_expired` — проверка кода работает, код не выдавался |

**Выводы анализа:**

1. Критических проблем нет: все не-2xx статусы — подтверждённые защитные отказы (RLS, RPC-права, auth-валидация) либо артефакты первых прогонов тестового скрипта;
2. РLS-политики отработали по матрице: гость получает 200 с пустыми приватными данными и 401/403 на запись;
3. В auth_logs зафиксированы `phone_provider_disabled` и `otp_expired` — соответствуют плану (SMS-провайдер подключается отдельно);
4. Паттерн «400 на POST» в edge_logs помог воспроизвести и починить тестовый скрипт (кодировка тел запросов) — пример диагностики по логам.

## 4. Типовые запросы для диагностики

<!-- PART2 -->
```sql
-- 4.1. Все 4xx/5xx за последний час: что именно падало
select event_message
from logs
where source = 'edge_logs'
  and (event_message like '%| 4%' or event_message like '%| 5%')
  and timestamp > now() - interval '1 hour'
order by timestamp desc;

-- 4.2. Ошибки входа: кто и почему не смог войти
select event_message
from logs
where source = 'auth_logs'
  and event_message like '%error%'
order by timestamp desc;

-- 4.3. Медленные SQL-запросы БД (> 500 мс)
select event_message
from logs
where source = 'postgres_logs'
  and event_message like '%duration%'
order by timestamp desc;

-- 4.4. Перегрузка пула соединений
select event_message, count(*)
from logs
where source = 'pgbouncer_logs'
  and timestamp > now() - interval '1 hour'
group by 1 order by 2 desc limit 20;
```

## 5. Процесс анализа логов с AI

Шаблон промпта (полный набор — `docs/frontend/ai_debugging_prompts.md`):

```
Роль: инженер, анализирующий логи бэкенда Supabase проекта «Капля».

Контекст: приложение PWA; API — PostgREST + RPC; RLS-политики;
ошибки клиенту отдаются как ApiError (коды в docs/api_reference.md, раздел 5).

Вход: выгрузка из Logs API/дашборда (edge_logs, auth_logs, postgres_logs) —
приложи сырые строки логов ниже.

Задача:
1. Сгруппируй события: нормальные / подозрительные / критичные.
2. Для каждого 4xx/5xx определи: компонент, вероятную причину,
   является ли отказ ожидаемым (RLS/валидация) или дефектом.
3. Сопоставь коды ошибок с матрицей ошибок ТЗ (разд. 6):
   корректно ли клиент получит сообщение?
4. Сформулируй гипотезы с проверяемыми шагами (SQL-запрос, curl-команда).
5. Предложи, что усилить: политики, индексы, rate limits, мониторинг.

Ограничения: не предлагай отключение RLS; не упоминай секреты в выводе.
```

Пример фактического применения — раздел 3 этого документа: по логам edge_logs
восстановлена хронология тестирования, классифицированы все 400/401/403
(ожидаемые отказы vs дефекты скрипта), найдена и устранена проблема кодировки
tel запросов при тестировании.

## 6. Рекомендации по мониторингу

- Раз в неделю просматривать: 5xx в edge_logs, ошибки в postgres_logs, warnings в auth_logs;
- после каждой миграции — проверить в postgrest_logs сообщение Schema cache loaded
  (число Relations/Functions должно соответствовать применённой схеме);
- при росте 401 в edge_logs — проверить срок JWT и работу refresh в клиенте;
- alert на квоты free tier (размер БД, egress) — дашборд Supabase → Settings → Usage.
