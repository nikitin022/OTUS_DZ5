# Выбор инфраструктурного решения

Документ фиксирует выбор серверной инфраструктуры проекта «Капля»: сравниваются два варианта и обосновывается итоговое решение на основе требований проекта.

## 1. Контекст

Проект «Капля» — PWA для доноров крови: карта центров крови, живая лента потребностей, запись на донацию. Фронтенд (React 18 + TypeScript + Vite) готов и хостится как статическое приложение; работа с данными изолирована за контрактом `ApiClient` (раздел 8 ТЗ), что позволяет подключить реальный бэкенд без изменения UI.

Схема базы данных PostgreSQL спроектирована (см. `docs/database_schema.md`, миграция `supabase/migrations/0001_initial_schema.sql`): 8 таблиц, связи, ограничения и индексы. Следующий вопрос — где эта база будет работать и какой слой API её обслуживает.

## 2. Требования проекта, влияющие на выбор

| # | Требование | Источник |
|---|---|---|
| T1 | Фронтенд — статическое PWA на GitHub Pages; API должен быть доступен по HTTPS с настроенным CORS | ТЗ, раздел 10 |
| T2 | Аутентификация по номеру телефона с одноразовым кодом (OTP) | ТЗ, разделы 3, 10 |
| T3 | Три роли с разным доступом к данным: гость (чтение), донор (свои записи/отклики/профиль), координатор (заявки своего центра) | ТЗ, разделы 3, 6 |
| T4 | Живая лента: автообновление заявок каждые 45 секунд; желательны push-обновления без поллинга | ТЗ, FR-3, FR-8 |
| T5 | Push-уведомления донорам по профилю (группа крови + радиус) | ТЗ, FR-4 |
| T6 | Ограничения безопасности: приватность персональных данных, достоверность заявок (статусы, модерация) | ТЗ, раздел 2 |
| T7 | Масштаб MVP: единичные пользователи и центры, небольшая команда без выделенного ops-инженера | ТЗ, раздел 10 |
| T8 | Схема БД — стандартный PostgreSQL; желательна переносимость (миграции — обычный SQL) | docs/database_schema.md |

## 3. Сравнение вариантов

### Вариант A — Supabase (BaaS)

Управляемый PostgreSQL + автоматически генерируемый REST API (PostgREST) + встроенный Auth + Row Level Security + Realtime + логи.

**Преимущества:**
- **Auth «из коробки»**: вход по телефону с OTP (T2) реализуется вызовом `signInWithOtp`, без собственной реализации доставки SMS и хранения кодов;
- **RLS-политики на уровне БД** (T3, T6): правила доступа описываются декларативно в SQL (`auth.uid()`), их невозможно «забыть» в коде endpoint'а; гость читает через `anon`-ключ с политиками только на чтение;
- **REST API генерируется автоматически** из схемы (PostgREST): endpoints для всех 8 таблиц доступны сразу после применения миграции — контракт раздела 8 ТЗ закрывается конфигурацией, а не написанием серверного кода;
- **Realtime-подписки** (T4): изменения в `blood_requests` можно слушать по websocket, вместо поллинга каждые 45 секунд (поллинг остаётся fallback'ом);
- **Логи и мониторинг** в панели проекта (api-логи, логи БД, auth-логи);
- **Нет ops-нагрузки** (T7): бэкапы, обновления, SSL, отказоустойчивость — на стороне платформы;
- **Бесплатный tier** достаточен для масштаба MVP.

**Недостатки / риски:**
- Привязка к платформе (vendor lock-in);
- Лимиты бесплатного тарифа (размер БД, трафик, пауза неактивного проекта);
- Серверная бизнес-логика (например, рассылка push) требует Edge Functions.

### Вариант B — Self-hosted (PostgreSQL в Docker на VPS)

Собственный VPS, Docker-контейнер PostgreSQL, собственный API-сервер (Node.js/Fastify/Express), собственная аутентификация.

**Преимущества:**
- Полный контроль над окружением и данными;
- Нет лимитов платформы;
- Свободный выбор расширений PostgreSQL;
- Ценный опыт инфраструктуры (Docker, реверс-прокси, SSL).

**Недостатки:**
- **Аутентификацию по телефону + OTP (T2) придётся реализовывать полностью самому**: генерация/хранение кодов, доставка SMS (платный сторонний сервис), сессии/токены, защита от подбора;
- **Авторизацию по ролям (T3, T6)** придётся дублировать в коде каждого endpoint'а — выше риск ошибок и SQL-инъекций;
- **API-сервер (T1, T4)** — дополнительный слой кода: валидация, маппинг моделей, пагинация, CORS, обновления зависимостей;
- **Ops-нагрузка (T7)**: VPS, обновления ОС и контейнеров, бэкапы, SSL-сертификаты, мониторинг доступности;
- **Push-уведомления (T5)** в обоих вариантах требуют отдельного сервиса — разница минимальна;
- Время до работающего end-to-end решения существенно больше.

## 4. Решение

**Выбран Вариант A — Supabase (BaaS).**

Критерии выбора — «требование → чем закрывается»:

| Требование | Чем закрывается в Supabase |
|---|---|
| T2 (телефон + OTP) | Supabase Auth `signInWithOtp` — генерация кода и сессии из коробки |
| T3, T6 (роли, приватность) | RLS-политики на уровне PostgreSQL, роли через `auth.uid()` + таблица `donors.role` |
| T1 (HTTPS + CORS для статического PWA) | Managed-домен проекта с HTTPS; CORS для REST настраивается в панели |
| T4 (живая лента) | PostgREST-эндпоинты + Realtime-подписки на `blood_requests` |
| T8 (переносимость) | Схема — стандартный PostgreSQL; миграции — обычные SQL-файлы |
| T7 (нет ops-ресурсов) | Бэкапы, обновления, SSL — на стороне платформы; логи в панели |

Решающие факторы: (1) аутентификация по телефону с OTP — самая рискованная для самостоятельной реализации часть (безопасность, SMS-шлюз), в Supabase она встроена; (2) RLS переносит контроль доступа на уровень БД, что соответствует требованию достоверности и приватности данных; (3) REST API генерируется из уже спроектированной схемы, поэтому контракт раздела 8 ТЗ закрывается почти без написания серверного кода; (4) для команды без ops-ресурсов управляемый сервис быстрее приводит к работающему end-to-end решению.

## 5. Риски и их снижение

| Риск | Снижение |
|---|---|
| Vendor lock-in | Схема БД — стандартный SQL без проприетарных типов; миграции переносимы в любой PostgreSQL; доступ фронтенда изолирован за контрактом `ApiClient` |
| Лимиты free tier (размер БД 500 МБ, трафик, пауза проекта после недели неактивности) | Мониторинг usage в панели; для production-сценария — переход на Pro-тариф |
| SMS-доставка OTP (провайдер, лимиты) | На этапе разработки — ограничение по тестовым номерам; для продакшена — настройка стороннего SMS-провайдера |
| Серверная логика (push-рассылки, интеграции) | Edge Functions в том же проекте; при миграции на self-hosted заменяются обычным сервисом |

## 6. Следствия для реализации

- Миграции БД хранятся в `supabase/migrations` и применяются в проекте Supabase (SQL Editor или CLI `supabase db push`);
- API — автоматически генерируемый REST (PostgREST) поверх схемы; кастомные операции добавляются через Postgres-функции / Edge Functions;
- Аутентификация — Supabase Auth (телефон + OTP); профиль донора связывается с учётной записью через `donors.auth_user_id`;
- Доступ — RLS-политики для ролей гость/донор/координатор;
- Секреты (URL проекта, `anon`-ключ) — в переменных окружения фронтенда, `service_role`-ключ не покидает серверный контур;
- Логи — Supabase Logs (API, Postgres, Auth).

Связанные документы: `docs/database_schema.md` (схема БД), `technical_specification.md` (требования, разделы 7–8).
